## Decisions made
- **Build lean, don't port** — pi-subagents' async substrate is ~6,000 LOC (incl. a 3,465-LOC detached runner); we took the PATTERNS (status.json/result-file/fs.watch/sendMessage) and built in-parent (~250 LOC) reusing our spawnSub. Oracle: "0 ported is accurate."
- **In-parent async, not detached** — completion = the spawn promise resolving (the parent holds it); the result-file/fs.watch machinery is cross-process-survival only. Detached = clean Tier A.5 escalation if survivability bites.
- **Enum verify table (security)** — `kind ∈ {test|typecheck|lint|build}` → fixed argv, `shell:false`, NO YAML env/cwd. The reference's `spawn(command,{env,shell:true})` was NOT ported (chain config is deny-additive + run_chain is LLM-callable ⇒ arbitrary exec from any repo unacceptable). Arbitrary commands deferred to a future global+trust-gated layer.
- **`auto` acceptance is badge-only, never rejects** — deliberate fork from the reference (which rejects on a missing report); preserves "existing chains unchanged" behaviorally.
- **Exit-reopen editor, not setHidden** — the `onHandle→setHidden` choreography Oracle prescribed did NOT reliably hide the clarify overlay (editor rendered behind). Switched to exit-reopen (resolve `custom()` with an `edit` signal → open `ctx.ui.editor()` with no overlay alive → re-open). More robust.
- **Strip BOTH volatile blocks for prompt-hash** — Oracle caught that the bridge block (`<bridge-context>`, with timestamp/entries/stale) is a second volatile driver alongside `<memory-context>`; a single-block strip wouldn't fix drift. Tagged the bridge block + strip both.
- **Per-job AbortController + registry** (Oracle's load-bearing add) — the tool-call signal is turn-coupled; background jobs need their own retained controller for `/stop`.
- **Oracle-review loop per group** — each group (1, 2, 1d/1e, prompt-hash, 3) was planned → Oracle-reviewed → I verified the load-bearing claims against live code (caught Oracle's stale "runWithWidget doesn't exist" claim) → revised spec → implemented → smoke → committed.

## Dead ends
- **`onHandle`/`setHidden` editor choreography** — Oracle prescribed `handle.setHidden(true)` before `ctx.ui.editor()` to hide the clarify overlay while the editor modal opens. Smoke-tested: the editor rendered BEHIND the overlay (setHidden didn't hide it — the dist showed `setHidden` barely used internally). Root cause: pi-tui's overlay model doesn't reliably support hide-while-nested-modal in our version. Fix: exit-reopen (resolve `custom()`, open editor alone, re-open). Saves sisyphus from re-trying setHidden.
- **Single-block prompt-hash strip (memory only)** — my first fix stripped only `<memory-context>`. Oracle read `bd-bridge.ts:128-167` and found the bridge block (`[FROM bridge, exported <ts>]` with timestamp/entries/stale) is a SECOND volatile driver, untagged (regex-fragile). A single-block strip would NOT fix drift. Fix: wrapped the bridge block in `<bridge-context>` + strip both. The lesson: enumerate ALL volatile composed-prompt emitters before claiming a strip is complete.
- **First-line-only prompt editing** — the plan's v1 scope initially dropped prompt editing (too hard); Oracle engaged the "modify afterward burns a full run" argument and mandated full multi-line edit via `ctx.ui.editor()` (not first-line, not embedded). Earlier I'd considered first-line only (reference `chain-clarify.ts:532`) — a false economy for our multi-line prompts.
- **`import { type X }` not elided by bare `node --experimental-strip-types`** — the background test couldn't import `agent-chain.ts` (which value-imports `chain-runner`/`spawn` carrying inline `import { type ExtensionAPI }` from pi-coding-agent, unreachable from bare node). node elides `import type { }` (whole-statement) but NOT `import { type X }` (inline modifier). Fix: extracted the pure helpers into a dependency-free `background-helpers.ts` (no pi-coding-agent import) so it's bare-node-testable. (pi's jiti handles inline-type fine at load; this is a bare-node-test concern only.)
- **`acceptance.ts` missing default factory** — pi loads every top-level `extensions/*.ts` as an extension and requires a default factory; `acceptance.ts` (a library) omitted it → pi failed to load ("Extension does not export a valid factory function"). Fix: added `export default function () {}` (same pattern as `chain-runner.ts`). The operator hit this as a startup failure.
- **Oracle's stale "runWithWidget doesn't exist" claim** — in the Group-3 review Oracle asserted the widget logic was "inline in execute()" and needed extraction. I verified against the live file: `runWithWidget` WAS extracted (commit a10a7ea, Group 1d/1e) at `agent-chain.ts:167`, called by `execute()` (:345) and `/chain-clarify` (:294). Corrected Oracle with evidence; the "extraction refactor" effort driver was moot. Lesson: even Oracle can read a stale version — verify load-bearing claims.
